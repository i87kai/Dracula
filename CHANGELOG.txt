Dracula v1.1.1
Release: 2026-08-17
============================================================

Fixed
-----
- Fixed the QEMU sandbox never starting. Dracula bound host port 8899 for its telemetry listener and then asked QEMU to forward the same host port inbound with "hostfwd=tcp::8899-:8899". QEMU could not bind a port Dracula already held, printed "Could not set up host forwarding rule" and exited about a second after launch, so the guest never booted and no dynamic analysis was ever possible.
- The forwarding rule was never needed. The telemetry link is outbound only: the host listens, and the GuestAgent dials out through the QEMU SLIRP gateway alias 10.0.2.2, which user-mode networking provides without any port forwarding. The inbound rule existed only to contend with the listener. It has been removed rather than moved to a different hard-coded port.
- Fixed telemetry from the guest being silently discarded. The deployed GuestAgent emits the original pipe-delimited text payload ("type|timestamp|category|message|details") while the host had moved to a length-prefixed binary payload. The packet framing is identical in both, so events arrived perfectly framed and then failed to decode: 2317 bytes on the wire, zero events. The host now detects and accepts both encodings, so a guest image provisioned before the format changed keeps working without being re-provisioned.
- Fixed legacy event type numbers being misinterpreted. The deployed agent numbers event types sequentially, from before the enum gained explicit values (Process = 38, File = 40, ...). A legacy "4" means the target exited but mapped to nothing in the current enum, so a finished sample was invisible and every session ran until it timed out instead of ending when the sample did. Legacy numbers are now mapped onto the current enum, and a session ends as soon as the target exits (34s instead of 94s in a measured run).
- Fixed guest telemetry never becoming findings. ThreatEvaluator::NormalizeSandboxEvents matched only the umbrella event values (Process, File, Registry, Network) while the guest emits the specific ones (ProcessCreated, FileModified, RegistryValueSet, NetworkConnect), so real telemetry produced no findings at all. Both are now accepted.
- Fixed the process id and process name never being transmitted. SerializeEventBinary wrote neither, so every event reached the host with pid 0 and an empty process name, which made the sandbox process tree unattributable. They are appended to the payload and read as optional trailing fields, so an older agent that does not send them still deserializes instead of having all of its events rejected.
- Fixed a shutdown deadlock in the telemetry listener. The worker thread blocked in recv() on a connected client, and Stop() closed only the listening socket before joining, so a guest that connected and then went quiet hung Dracula on exit. Reads are now polled with a timeout and the client socket is closed from the caller's thread; Stop() returns in milliseconds with an idle client attached.
- Fixed a launch failure being reported as success. StartQemu returned true whenever CreateProcess succeeded, even when QEMU rejected its arguments and exited immediately afterwards, which is exactly what the port conflict did. QEMU's stderr is now captured, the process is verified alive after a settle window, and a refused configuration is reported with QEMU's own message.
- Fixed the sandbox ignoring configuration. RunDynamicSandbox built default VMConfig and TraceOptions rather than reading the configured ones, so the listen address, port policy and timeouts set in config.ini never reached the sandbox.

Added
-----
- Collision-safe port allocation (host/port_allocator). Ports are claimed by an actual bind and the live socket is handed to the caller, so there is no check-then-bind window for another process to slip through, and the caller always learns the port that was ACTUALLY bound rather than the one requested. Sockets are released on every failure path.
- Three configurable port strategies: "fixed" (use the configured port or fail), "preferred-then-range" (try the configured port, then scan a range, then fall back to an OS-assigned port) and "ephemeral" (let the OS choose). The default prefers the configured port, so an already-provisioned guest keeps working and Dracula only moves when the port is genuinely taken.
- SO_EXCLUSIVEADDRUSE on the listening socket, replacing SO_REUSEADDR. On Windows SO_REUSEADDR lets a second socket bind an address another socket is already using, which is precisely the collision the allocator exists to detect; exclusive use turns a conflict into an honest, reportable failure instead of a silent double bind.
- Guest session handoff (host/guest_session_handoff). The host writes dracula_session.ini into the shared folder before QEMU starts, carrying the host address, the port that was actually bound, the session id and the timeout. QEMU snapshots the share into a read-only FAT drive at launch, so writing it beforehand is the only ordering that works.
- GuestAgent reads the handoff from the shared drive when no --host-port argument is supplied, and an explicit argument still wins, so a guest provisioned with a fixed port is unaffected.
- guest_share/auto_exec.bat now reads the handoff and passes the port through, falling back to the historical default when no handoff is present.
- Separate connect and execution budgets. The connect budget covers guest boot and auto-login and runs from launch; the execution budget covers the sample and only starts once the agent is on the line. Sharing one budget meant a 60 second execution limit silently capping a four minute boot.
- Telemetry diagnostics: bytes on the wire, events decoded and framing resynchronisations are counted and reported, which is what separates "the agent sent nothing" from "the agent sent something the host could not decode". These are very different faults and used to look identical.
- Actionable diagnosis when the agent never connects. If the listener had to move off the configured port, the message says so and explains that a guest provisioned before the handoff existed dials the configured port directly and cannot follow the move.
- QemuManager::BuildCommandLine, so the launch arguments can be asserted on without booting a guest.
- tests/test_sandbox_network.cpp: 98 checks covering port availability and allocation, conflict fallback across all three strategies, exhausted ranges, listener lifecycle and socket release, prompt shutdown with an idle client, protocol framing across split reads, both payload encodings, legacy event type mapping, the session handoff, the QEMU command line, and network configuration.

Verified
--------
- Clean Release build (GCC 16.1.0 MinGW-w64, CMake 4.3.3, Release) with no warnings or errors in project-owned code.
- Full suite: 226 terminal UI, 198 anti-evasion, 112 analysis core, 98 sandbox networking, test_emulate_buffer. 634 checks, 0 failures. CTest 5/5.
- REAL QEMU GUEST RUN, end to end: QEMU launched and stayed up, the Windows guest booted, GuestAgent connected after 32s on port 8899, 2317 bytes and 34 telemetry events were received and decoded with 0 framing errors, the target process was tracked from spawn (PID 4832) to exit (code 0), the session ended when the sample finished, QEMU was terminated, the base disk image was left byte for byte unchanged, and the port was released. No port conflict occurred.
- The received telemetry is the environment probe's full output read from inside the guest, including HYPERVISOR_BIT=1, HYPERVISOR_VENDOR=Microsoft Hv, FIRMWARE_MARKER=QEMU, API_PROCESSOR_COUNT=2 and SLEEP_TICKCOUNT_MS=531 against SLEEP_QPC_MS=529, which independently confirms the sandbox environment fingerprint reported by the anti-evasion engine.
- Port conflict scenario, with another process holding 8899 during a real QEMU run: the listener moved to 8900, wrote 8900 into the handoff, and QEMU launched normally instead of exiting. The guest did not follow the move, because the image was provisioned with a startup script that dials 8899 directly; Dracula reports exactly that and names the two ways to resolve it.

Known limitations
-----------------
- A guest image provisioned before this release runs a startup script and a GuestAgent that predate the session handoff, so it always dials the configured port. It works normally while that port is free, which the default policy ensures wherever possible, but it cannot follow a fallback port until setup_lab.bat is re-run inside the guest from the updated share.

Dracula v1.1.0
Release: 2026-08-17
============================================================

Added
-----
- Anti-Evasion Intelligence Engine. A first-class subsystem that detects, locates, explains and experimentally verifies code that changes its behaviour when it believes it is being analysed. It unifies static detection (Capstone, CFG, XRefs, imports, data-driven artifact rules) with controlled execution under explicit environment profiles, differential re-execution, and evidence correlation.
- /antievasion command, with aliases /antivm, /evasion and /ae, registered through the central command registry so tab completion, the palette, /help, history and argument completion all work with no per-command special cases. Flags: --detect (default), --compare, --details, --profile <name>, --no-emulation.
- Scripted CLI equivalents Dracula.exe --anti-evasion <file> [--compare], sharing the same engine as the REPL command. There is no second implementation.
- EnvironmentProfile: the single place that decides what a sample running inside a Dracula analysis environment can observe about its host - CPU identity, CPUID answers, topology, memory, disk, firmware, MAC prefix, screen, uptime, input activity, debugger state and timing policy. Three profiles ship: Baseline (Dracula's default, honest about being an analysis environment), Realistic (ordinary desktop characteristics with virtualization evidence left intact), and AnalysisFriendly (selected indicators normalized so environment-gated paths become reachable).
- VirtualTimeState: a coherent multi-clock model. RDTSC, RDTSCP, QueryPerformanceCounter, GetTickCount, GetTickCount64, timeGetTime and system uptime are all derived from one logical nanosecond counter, so they cannot disagree. An accelerated Sleep(5000) advances every source by 5000 ms together, which is exactly the consistency a sophisticated sample cross-checks for.
- CPUID is now answered from the active profile through Unicorn's instruction hook: vendor string, family/model/stepping, logical processor count, the hypervisor-present bit (leaf 1 ECX[31]), the hypervisor vendor leaf (0x40000000), topology leaves and the brand string.
- RDTSC and RDTSCP interception. Unicorn provides no instruction hook for either, so the encodings are recognised in the code hook, the registers are filled from the virtual clock and the program counter is stepped past the instruction. SIDT/SGDT/SLDT/STR/SMSW are recorded as evidence and left to execute natively rather than fabricated.
- BranchInfluenceTracker: bounded, register-granular environment provenance. It follows an environment value from the instruction or API that produced it, through data movement and a small stack-spill and output-buffer map, into the compare that sets the flags and the conditional branch that reads them. This is what separates "the program asked" from "the answer decided what ran", and it is the main input to the confidence model.
- EnvironmentConsistencyGraph: environment facts are modelled as claims made by a particular observable channel (CPUID, OS API, firmware, device metadata, timing). Two channels disagreeing about the same property is a contradiction, reported as PROFILE_COHERENCE_WARNING, because hiding one virtualization marker while exposing a contradictory one makes an environment MORE fingerprintable, not less. Every profile is validated before use.
- Differential execution. --compare runs the same sample under several profiles and compares reached basic blocks, reached functions, branch directions, HLE call sets, instruction counts and termination reason, producing an ExecutionDelta and a set of BranchDivergence records naming the exact RVA that went the other way and what each path led to.
- Environment Sensitivity Score, 0-100, on its own axis and deliberately NOT the malware threat score. Static detection contributes a capped floor of 25; the rest comes from observed divergence. Documented in DRACULA_GUIDE.md.
- Execution coverage recording in Unicorn (basic blocks, functions, branch directions) as sets and counters rather than per-address lists, plus a deterministic BehaviorFingerprint per run suitable for regression testing.
- Normalization audit trail. Every value Dracula supplies that differs from Baseline is recorded with its baseline value, supplied value, source and reason. Dracula never changes what a sample sees without saying so.
- Environment-aware Win32 HLE handlers: GetSystemInfo, GetNativeSystemInfo, GlobalMemoryStatusEx, GetPhysicallyInstalledSystemMemory, GetSystemMetrics, GetLastInputInfo, GetComputerNameA/W, GetUserNameA/W, GetDiskFreeSpaceExA/W, GetSystemFirmwareTable, RegOpenKeyExA/W, SleepEx, GetTickCount64 and timeGetTime, all answering from the active profile and recording an observation.
- Data-driven artifact rule table replacing scattered string comparisons. Each rule carries its provider, artifact type, category, base confidence and a note on why it is (or is not) meaningful. A bare vendor name is scored as the weak evidence it is; a CPUID hypervisor signature is not.
- SandboxEnvironmentFingerprint: what Dracula's configured QEMU guest actually looks like from inside it, stated as an explicit list of observable properties with a fingerprintability score. It does not claim invisibility.
- MCP tool analyze_anti_evasion, and an anti-evasion summary embedded in analyze_file. Both call the same engine; MCP holds no anti-evasion logic of its own.
- Anti-evasion sections in the JSON, Markdown and terminal reports. JSON carries structured fields (techniques, differential_runs, branch_divergences, profiles, normalizations), embedded as a real nested object, never as formatted text.
- Benign deterministic probe samples, built from source at build time: ae_cpuid_gate, ae_timing_gate, ae_resource_gate, ae_debug_gate, ae_combined_gate and ae_benign_sysinfo. None contains a payload; each inspects one environment property and takes one of two harmless code paths.
- samples/antievasion/environment_probe.c, a benign program that prints environment ground truth as KEY=VALUE, usable natively and inside the guest to prove a profile is real rather than documentation only.
- tests/test_anti_evasion.cpp: 198 checks across taxonomy, clock coherence, profile validation, artifact rules, provenance, CPUID and RDTSC machine code, static detection, differential execution, false positives, combined signals, CFG/XRef correlation, fingerprint determinism, scoring, serialization, command registry, session integration, MCP, sandbox fingerprint, bounds and observation mode.

Changed
-------
- ThreatEvaluator now weights evasion evidence by context. On its own it is halved and capped at 15 points, so no amount of virtualization detection can carry a verdict by itself; alongside independent malicious evidence it counts in full, capped at 25, because that is when evading analysis is meaningful. Anti-VM is not malware: development tools, games and licensing systems all inspect their environment legitimately.
- The static gate scan now continues past a call instead of stopping at it, so the very common "call IsDebuggerPresent; test al, al; je" shape is detected rather than missed.
- EmulationResult carries coverage, environment observations, branch observations, the active profile name and the logical elapsed time. All are empty unless a run asks for the instrumentation, so ordinary /analyze and /emulate pay nothing for it.
- The QEMU sandbox fingerprint resolves config/config.ini through the standard resource path, so it describes the guest that is actually configured rather than the built-in defaults.

Fixed
-----
- HleCallRecord.callerRva was never populated, so every HLE call in a report pointed at RVA 0. It is now set from the caller's return address.

Verified
--------
- Clean Release build (GCC 16.1.0 MinGW-w64, CMake 4.3.3, MinGW Makefiles, Release) with no warnings or errors in project-owned code.
- 198 anti-evasion checks pass, 226 terminal UI checks pass, 112 analysis-core checks pass, test_emulate_buffer passes. 0 failures.
- Real differential demonstration: build/samples/antievasion/ae_cpuid_gate.exe scores 72/100 environment sensitivity. Baseline reaches 4 blocks and 3 functions and takes the branch at RVA 0x10D5 to an early exit; AnalysisFriendly falls through the same branch and reaches 18 blocks and 8 functions. The divergence is attributed to CPUID (hypervisor presence) by the provenance tracker. ae_combined_gate scores 84/100 with three independent gates reported separately plus one overall conclusion.
- False-positive control: ae_benign_sysinfo queries CPUID, the processor count, the performance counter and the tick count without gating on any of them. It scores 14/100, reaches identical coverage (11 blocks, 5 functions, 217 instructions) under all three profiles, and no technique is claimed to control flow.
- Threat restraint confirmed: ae_cpuid_gate scores 72/100 environment sensitivity but only 12/100 threat, reported as Clean / Benign.
- Real MCP round trip against a benign anti-VM sample returns the structured result on a single line, keeping stdout pure JSON-RPC.
- Interactive session verified end to end: /help antievasion, /analyze, /antievasion, /antievasion --compare, /findings, /report json and /session, with the fixed-header scrolling layout intact.

Known limitations
-----------------
- Live QEMU guest verification is BLOCKED BY ENVIRONMENT. Dracula's telemetry listener binds host port 8899 before launching QEMU, whose "hostfwd=tcp::8899-:8899" rule needs the same host port, so QEMU exits immediately with "Could not set up host forwarding rule". Confirmed by diagnosis: port 8899 is free, and QEMU starts normally with that rule when Dracula is not already listening. This is a pre-existing defect in the QEMU sandbox path, independent of the anti-evasion work, and it is not fixed here. QEMU sandbox support in this release is therefore limited to environment fingerprinting, which does not require booting the guest.
- Static branch correlation is intraprocedural. A check whose conditional branch lives in a different function than the check itself is caught by the dynamic provenance tracker, not by the static scan.
- Provenance is register-granular with a bounded stack-spill and output-buffer map. It drops marks it cannot follow (arbitrary memory, SIMD, indirect control flow) rather than guessing, so it under-reports rather than inflating confidence.
- Windows exception-based anti-debug semantics are not modelled in Unicorn. Such patterns are reported as detected statically and are explicitly not claimed to be modelled.
- No virtual environment can be made indistinguishable from physical hardware. Dracula reports what its environments expose; it does not claim to hide them.
